Same agent. Different accountability.

Vibe coding

Agentic engineering

The agent writes the code. You keep the quality bar.

Karpathy coined “vibe coding” in February 2025 for a style where you accept everything and stop reading the diffs. His line was, “I ‘Accept All’ always, I don’t read the diffs anymore,” and he said it was fine for throwaway weekend projects. Simon Willison’s short definition is building software with an LLM without reviewing the code it writes.

That is fine for a prototype, a throwaway script or a weekend experiment with no client data, no secrets and nothing charged per use. It is not how I build something that other people will rely on.

For real work, Karpathy now uses another name: agentic engineering. It is the same agents, “except with more oversight and scrutiny.” The agent writes most of the code, while I keep the quality bar through gates, tests and review.

I kept “vibe coding” in the title because everyone knows the phrase. What this cookbook teaches is agentic engineering.

Think of this as an autonomy slider, an idea Karpathy talks about. I do not pick “AI or no AI”; I pick how much autonomy fits the stakes. Lower stakes mean fewer gates. Higher stakes mean more tests, review and explicit approval.

In the workflow, the same skill proposes a TRIVIAL, LIGHT or FULL path for every change, and I confirm it. TRIVIAL is copy, a typo, documentation or a config value: no new files and no tests touched. I edit directly, run the relevant tests and confirm.

LIGHT is at most about fifty non-test lines across no more than three files, with no new dependency, folder, ADR or authentication surface. The failing tests still come first. FULL is the default: specification, failing tests, build, verification, review, documentation and three gates.

The kit uses the same idea at project level. Starter fits a prototype or a first week with agents. Standard fits most real projects. Full adds the role subagents and the task skill with approval gates for production code and client deliverables.

When in doubt, I pick FULL. A skipped step costs more than it saves.

Part0

Pen and paper

Define done before you prompt.

Before the agent does anything, I decide what I want, what finished looks like and how I will check it. Five lines on paper keep the agent from steering me into work I never asked for.

SOURCES · COOKBOOK.md:73-106

Write five lines before every prompt

Goal
Done when
Out of scope
Approach
How I check
then: plan mode

No “Done when”? You’re not ready to prompt.

Every workflow starts before you open the agent. If you skip this step, the agent will pull you away from your own train of thought with thousands of lines of code and over-complex solutions you never asked for. It is very easy to get lost in what your agent is building.

Five lines are enough. The one that matters most is “Done when”: two to four checks you can see with your own eyes. If you can’t fill it in, you’re not ready to prompt. Talk to the business, read the notes again, or ask the agent to interview you first; that’s the grill-me skill, coming up in Part 3.

The other lines are the goal, what is out of scope, the approach I expect, and exactly how I will check the result. The digital equivalent is plan mode. The agent can read files, run exploratory commands and ask questions, but its edits stay blocked until I approve the plan. The paper holds my intent, the plan holds the agent’s interpretation, and I compare the two.

In Claude Code I cycle to plan mode with Shift+Tab. Copilot, Codex and Cursor also provide plan modes; the exact shortcut depends on whether I am in the IDE or CLI.

WATCH · In Claude Code, a terminal session started with bypass permissions available turns plan mode into an instruction only. Planning may still run approved shell commands; only file edits are blocked.

Part1

Who owns what

Decide what stays with you.

The first setup decision is not the model or the tool. It is what the agent may change on its own and what stays with me.

SOURCES · COOKBOOK.md:107-140

Own the gates. Delegate the writing.

You own

  • deploys
  • secrets
  • git history
  • new dependencies
  • final sign-off

You delegate

  • specs
  • tests
  • docs
  • most of the code

The first decision is not which model or which tool. I decide what the agent may change on its own and what stays behind a human gate. For me this is the most critical part of the setup.

I own DevOps and infrastructure, secrets, git history, every new dependency, the agent’s own setup files, architecture decisions, contracts from outside the team, and final acceptance. The agent can draft options and reasoning, but I make these decisions and approve the change.

I delegate product requirements plans, task specs and acceptance criteria, issue records and their lessons, tests written by a separate tester agent, skills and memory, documentation, and most of the code.

Why delegate most of the code? Because I cannot read hundreds of thousands of lines myself, while agents can write thousands in minutes. I do not validate every line, and I do not think anyone should try. Not reading every line does not mean not checking; it means checking behaviour and reading by risk.

SOURCES · COOKBOOK.md:107-128 (ownership table, trimmed wording)

Check behaviour, not lines. Read by risk.

I validate behaviour, not lines. I use tests written before the code by a different agent, which the coding agent cannot edit; an independent reviewer that re-runs everything and reads the diff; static checks on every change; hooks that block the agent from touching what I own; and my own end-to-end check before I accept anything. Parts 4 and 5 show each mechanism on a real project.

Not every line deserves the same attention. I read the code myself where a mistake is expensive or hard to notice: money and pricing, security and authentication, client data, and core business rules. On the project that means the domain layer, where prices, VAT and service-level rules live. One bug the reviewer caught was a VAT total.

One rule has no exceptions: I never ship code I could not explain to someone else. Simon Willison puts it this way: “I won’t commit any code to my repository if I couldn’t explain exactly what it does to somebody else.” When I need to understand code I did not write, I ask the agent: “Read the source and then plan a linear walkthrough of the code that explains how it all works in detail.” That works in any agent.

Client data: what leaves, what steers the agent

Check the firm’s policy and the contract first.

Two questions come before I point an agent at client work. First: what leaves my machine? The model runs at the provider, so what the agent reads to do the task goes there: my prompts, the files it opens, and the output of its commands.

On business plans, none of the three tools trains on your data by default. Claude Code under commercial terms: no training, 30-day retention by default, zero data retention available per organisation on request. Copilot Business and Enterprise: GitHub states it does not use that data to train models. But note that Copilot’s content exclusion does not apply in agent mode. Cursor: Privacy Mode means your code is never used for training, and it is on by default for Enterprise teams.

Second: what can steer the agent? Anything it reads can carry instructions: a README, an issue, a web page, or an MCP tool’s output. That is indirect prompt injection, OWASP’s number one LLM risk. Simon Willison calls the combination of private data, untrusted content and external communication the lethal trifecta. If an agent has all three, I assume someone else may be able to steer it.

I make no claim here about the firm’s own policy. Before an agent sees client code or data, I check the firm’s policy and the client contract.

WATCH · Personal plans (Free, Pro) have different training terms. Cursor’s Privacy Mode is about training, not zero retention; Cursor lists exceptions. Claude Code’s security page: “no system is completely immune to all attacks”. For MCP: “Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk.” Don’t quote a single 28-day retention figure for Copilot in the IDE; GitHub’s 28 days apply to Chat on github.com and to Copilot Memory.

Git is your undo button

Agents make mistakes: a wrong assumption, a refactor that breaks three other things, a “fix” that deletes the feature it was meant to repair. So before you let an agent work, make sure you can always get back to the last state that worked. That way is git, and you set it up before the task, not after the damage.

I start clean and commit often. A commit is a save point. Addy Osmani’s phrase is: “Frequent commits are your save points - they let you undo AI missteps and understand changes.” In the project, the task skill refuses to start without a clean git status, and it commits at two gates: when the failing tests are approved, and when the task is done.

I experiment on a branch, never on main. If it fails, I delete the branch and return to the last good commit.

Claude Code saves a checkpoint at every prompt, and /rewind or Escape twice restores it. But checkpoints don’t track files changed by shell commands, and subagent edits are usually not restored. The docs literally say “Use git to revert them.” In a workflow built on subagents, git is the only real undo.

The commands I keep close are git status to see what changed, git diff to inspect it, git restore for one uncommitted file, git stash to park work, git revert to undo a commit while preserving history, and git reset --hard to return to a known good commit. The last command destroys work. That is why the project denies it to the agent: it is my command, not the agent’s.

SOURCES · COOKBOOK.md:247-285

Lay the foundation top-down

Every later agent reads this foundation.

I work from top to bottom: value first, then requirements, architecture, tasks and finally code. Every later agent reads this foundation, so mistakes here spread through everything downstream.

I start with an empty repository and ask the agent for the skeleton: product and architecture docs, decisions, issues, workflow lessons, task folders, tests and a short CLAUDE.md. I ask it to show me the tree before creating anything.

The structure makes the order physical. Raw inputs and PRPs live under product docs; architecture records principles, current state and one short record per decision; every task gets its own folder and leaves a file at each step. Code comes last, written against tests created first.

I collect every raw input as it arrived: stories, requirements, emails, call notes, transcripts and screenshots. I keep its source and date, translate everything into one shared language, and preserve the original meaning. In the project, the written specification stayed verbatim and the accompanying commentary was stored as a translation.

SOURCES · COOKBOOK.md:247-309 (2.1 skeleton prompt, 2.2 raw inputs)

One PRP cuts every task

I give the raw-input folder to the agent and ask for one PRP. The term has two useful meanings. In Rasmus Widing’s framework, Product Requirement Prompt means a PRD plus curated codebase intelligence and an agent runbook: what to build, the context needed to build it, and the steps and checks to follow.

In our project, product requirements plan means one document per milestone. It fixes the goal, audience, scope, rules and ordered task list. Every task specification is cut from that one document, so the plan remains the shared source rather than being reinterpreted task by task.

Three things matter in ours. It opens with must-know facts, including that the LLM never owns business truth. The goal is a business outcome—approval for a 90-day pilot at one site—not a feature. And the cut rule is explicit: if M2 is not reached by day 10, SHOULD and COULD items drop and the remaining time goes to rehearsal.

I read the PRP line by line. It is short enough to do that, and everything downstream inherits its mistakes.

Least code comes first

Before I build, I ask the agent to research existing solutions, libraries and reference repositories. Our first non-negotiable is least code: the best code is the code never written. I walk this ladder in order and write new code only as the last resort.

The agent’s knowledge is stale, so I do not let it rely on memory for a third-party API, command or configuration key. On a previous project, a wrong assumption about a Snowflake connector call was baked into the fakes, so no test could expose it; behaviour was checked on pandas 2.2.3 while the repository pinned 2.3.3. The rule is installed version, then Context7, then official docs.

I also make architecture decisions together with the agent. It brings two or three options, least-code first, with evidence; I decide. It must never record a decision I have not approved. Each decision becomes a short ADR. The example in the cookbook is 32 lines.

The last ADR section is “Revisit when”. I write down in advance what evidence would change the decision, so it can be firm today without pretending to be permanent.

Architecture itself stays live. The doc-keeper edits it in place at the end of every task, and history lives in git and task folders. I freeze only an external design contract that the team does not own; everything we own describes the current state.

The components

Configure what surrounds the model.

I treat a coding agent as more than the model in the terminal. Here I separate the instructions file, memory, skills, subagents and tools, and show what each is for.

SOURCES · COOKBOOK.md:461-480

CLAUDE.md is a roadmap, not an encyclopedia

Told it twice? It goes in.

CLAUDE.md is the file I ask every colleague to read line by line, because it shapes everything the agent does afterwards. It loads at the start of every session, and custom subagents receive it too. A vague or bloated roadmap produces vague or bloated work across the project.

It tells the agent what we build, where specifications, decisions, issues, tests and code live, which agents and skills to use, the project structure, and the environment quirks that have already cost us time. Every line in our environment section exists because the agent got it wrong at least once.

I use two tests. Mine is on the slide: if I have told the agent the same thing twice, it goes in. The opposite test, suggested by Anthropic, is to ask of every existing line: would removing this cause Claude to make mistakes? If not, cut it.

Long files get ignored. Ours is 132 lines. The actual guard is stricter than the general “under about 200” advice: its CLAUDE.md size rule warns at 150 lines and blocks above 200.

For mixed teams, AGENTS.md is the shared open format read by Copilot, Codex, Cursor and other agents. Claude Code reads it by default only when there is no CLAUDE.md, so I keep shared rules in AGENTS.md and make CLAUDE.md a thin wrapper that imports it, followed by any Claude-specific instruction.

WATCH · Memory has layers: managed policy, user, project, local, subdirectory, rules with and without paths, and auto memory. After compaction only the root CLAUDE.md and unscoped rules are reliably back in context, so critical rules go there. Imports keep files tidy but don’t save context: imported files still load at launch, up to four hops deep.

Skills load only what they need

A skill is a workflow I run often, with a fixed structure and order. I write it down once as a folder with a SKILL.md, and the agent follows it when it recognises the situation or when I type its name. My own example is presentation work: instead of repeating the same colours and rules, I put them in a skill.

Skills scale because they load lazily. At startup only the name and description load. The body loads when the skill is used. Reference files load only when a step needs them, and scripts run without being read into context. Our prompt-writing skill is 186 lines, with 3,024 lines of guides and templates behind it that cost nothing until needed.

A skill can also be tiny. Grill-me says: “Interview me relentlessly about every aspect of this plan until we reach a shared understanding.” Then: “Ask the questions one at a time.” If a question can be answered by exploring the codebase, it tells the agent to explore instead of asking me. I use it before a PRP, architecture decision or spec because it finds gaps while they are still cheap to fix.

WATCH · Pitfalls: all descriptions share a budget of about 1% of the context window, so write them tightly, and a description shouting “MUST BE USED” makes a skill fire when it should not. Skills that should run only on request get disable-model-invocation: true. For writing skills, Anthropic publishes skill-creator in the claude-plugins-official marketplace; it builds evals and tunes descriptions. The same SKILL.md format works in Copilot, Codex and Cursor.

SOURCES · COOKBOOK.md:580-716 · code.claude.com/docs/en/skills · github.com/mattpocock/skills · github.com/anthropics/skills (verified 2026-09-28)

Read it before you install it

Before I recommend skills, a warning. Skills, hooks and plugins from the internet are code and instructions written by strangers, and they run on my machine with my permissions. A skill enters the agent’s context as instructions it will follow. A hook is a shell command.

This is not theoretical. In February 2026 Snyk scanned 3,984 public skills: 36.82% had at least one security flaw, 13.4% had a critical one, and Snyk confirmed 76 malicious payloads designed for credential theft, backdoors and data exfiltration.

Claude Code’s plugin security docs warn: “Command hooks execute shell commands with your full user permissions. Claude Code runs hooks and MCP servers outside the sandbox.” GitHub gives Copilot users the same warning: “Skills are not verified by GitHub and may contain prompt injections, hidden instructions, or malicious scripts.”

So I read the whole SKILL.md and every script before installing it. If I cannot understand a script, I do not install it. I prefer official marketplaces and authors I know, and I review again after updates because auto-update can change files. I treat a cloned repository the same way: its .claude folder can define hooks and MCP servers. Check Point found two now-patched ways such files could run code earlier and advises inspecting .claude and .vscode before opening a project.

WATCH · Use 76 for malicious payloads; Snyk’s headline blurs it with the 1,467 skills that had any flaw. Check Point’s disclosure covers two CVEs (CVE-2025-59536 and CVE-2026-21852). For Copilot, GitHub suggests inspecting a skill with gh skill preview.

Subagents must leave a file

A subagent is the same coding agent, specialised for one job: its own instructions, its own tools, sometimes its own model. The important property is isolation. Claude Code’s docs say: “Each subagent starts with a fresh, isolated context window. It doesn’t see your conversation history.”

That isolation is both the point and the price. The main context stays clean, several subagents can run in parallel, and I can give each one least privilege. But the main agent only sees the final summary, the subagent knows nothing I did not put in its prompt, and multi-agent runs cost roughly 15 times the tokens of a chat.

That is why every subagent must leave an artifact. In our project it is a strict contract: each role writes one file at a fixed path, line 1 is a verdict such as READY or BLOCKED, and the final reply is only the verdict and the path. The main agent checks the file and passes it to the next subagent. That is how context moves between agents that cannot see each other, and it leaves a record I can read later.

WATCH · Transcripts are saved on disk and kept 30 days by default, and a subagent can be resumed with SendMessage, so “stateless” is too strong; think “isolated, and effectively gone when the session ends”. Subagents can spawn subagents up to three levels deep; our previous project ended up with “186 ad-hoc agent types”, so now only the main thread delegates and every agent has Agent on its deny list.

SOURCES · COOKBOOK.md:717-812 · code.claude.com/docs/en/sub-agents · anthropic.com/engineering/multi-agent-research-system (verified 2026-09-28)

Teams and MCP: keep both small

Two components I use sparingly. Agent teams start with a lead and several teammates. It is easy to assume they share one context window; they do not. Claude Code’s docs say: “Teammates work independently, each in its own context window.” What they share is a task list and a mailbox. That makes teams useful for brainstorming, debating competing bug hypotheses or multi-angle review. They use significantly more tokens than a single session, and the feature is experimental, so we keep it off in this project.

MCP servers give the agent extra tools. A year ago I needed several. Today I use three: Context7 for current library docs, Playwright so the tester can click through the real UI, and a cloud provider’s server when I am building infrastructure.

If a CLI exists, like gh, aws or az, the agent can simply run it, and that is often cheaper. Claude Code’s best-practices guide says: “CLI tools are the most context-efficient way to interact with external services.” Microsoft makes the same point about its own Playwright MCP alternative.

The same pattern carries across agents

Same ideas, different folders.

The all-green matrix means the capability exists, not that the implementation is identical. Claude Code, Copilot, Codex and Cursor all support instructions, skills, subagents, hooks, plan mode and MCP. A Claude Code setup therefore carries over surprisingly well.

I keep the folder map in the notes rather than making people read paths from the screen. Claude Code: CLAUDE.md; .claude/skills/; .claude/agents/; hooks in .claude/settings*.json; Shift+Tab for plan mode; .mcp.json for project MCP servers.

Copilot: AGENTS.md, .github/copilot-instructions.md and .github/instructions/*.instructions.md, with CLAUDE.md available in VS Code; skills in .github/skills/, .claude/skills/ or .agents/skills/; subagents in .github/agents/*.agent.md; hooks in .github/hooks/*.json; /plan in VS Code or Shift+Tab in the CLI; MCP in .vscode/mcp.json, .mcp.json, ~/.copilot/mcp-config.json or .github/mcp.json.

Codex: AGENTS.md; skills in .agents/skills/; TOML subagents in .codex/agents/; hooks in .codex/hooks.json or config.toml; /plan; MCP in ~/.codex/config.toml or a trusted project’s .codex/config.toml.

Cursor: AGENTS.md and .cursor/rules/*.mdc, with CLAUDE.md in the CLI; skills in .cursor/skills/, .agents/skills/ or .claude/skills/; subagents in .cursor/agents/ or .claude/agents/; hooks in .cursor/hooks.json and Claude Code settings; Shift+Tab in the IDE or /plan in the CLI; MCP in .cursor/mcp.json.

What does not transfer blindly is the hook contract. Payloads and exit-code conventions differ, so a guard written for one tool needs its own tests in every other tool. Cloud agents also change the plumbing: GitHub’s Copilot cloud agent works on a branch in an ephemeral Actions environment, so the gates become pull-request reviews.

Part4

Running the workflow

Take one task to verified commit.

With the pieces in place, I run one task from an idea to a verified commit. I write down each decision and issue, and leave a file at every step.

SOURCES · COOKBOOK.md:918-950

One task, three gates

Tests first. Code second.

This is the loop. One skill, /task, drives it. The main agent orchestrates, a specialised subagent does each stage, and I approve at three gates.

I start with intent. The planner writes the spec, and I approve it at G1. The tester writes failing tests from that spec, and I approve them at G2. They are committed and locked. Only then does the developer write the smallest change that makes them pass.

The tester returns and runs the full suite. A failure goes to the debugger for at most two rounds, then I decide. The reviewer reads the diff against the spec; requested changes go back to the developer. The doc-keeper updates the current documentation. At G3, I test the result end to end before the task is committed.

The order matters. Tests written after code tend to describe what the code does, not what it should do. A developer who did not write the tests also cannot quietly bend them.

Green means green. The tester compares the set of failing test IDs with the baseline, never just the count. Five failing before and five failing after can hide one fixed test and one newly broken test.

The suite grows with every task and runs in full every time. This task took the backend suite from three tests to 128, and every later task runs all of them. A new feature that breaks an old one should show up immediately.

I also prove that an important test can fail before trusting its PASS: temporarily neuter the code, watch the test fail, then restore it. A test that cannot fail proves nothing.

Not every change needs the full loop. FULL is the default. LIGHT keeps tests first but merges the spec and test gates for a small change. TRIVIAL is for copy, a typo, documentation or a configuration value. When in doubt, I choose FULL.

Issues are shared memory between agents. The planner and debugger search the catalog first, so one problem has one record. Part5

Guardrails

Turn critical rules into enforcement.

I cannot rely on guidance alone: the model can forget it. I move the rules that matter into permissions, hooks, linters and tests, where the tool enforces them.

SOURCES · COOKBOOK.md:1232-1263

Guidance is advice. Enforcement holds.

In Part 1 I promised to explain how to protect what belongs to you. I think this is the most important part: everything else is advice the agent usually follows, and guardrails are the rules it cannot skip.

There are two kinds of rules. Guidance, such as CLAUDE.md, skills and prompts, is read by the model, and it can forget it in a long session, after context compaction, or when one rule is lost in a long file. Enforcement, such as permissions, hooks, linters and tests, is run by the tool itself and holds whether the model remembers or not.

As the Claude Code best-practices guide puts it: “Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens.” Use hooks for actions that must happen every time with zero exceptions.

My rule of thumb is simple. If breaking a rule causes real damage, such as a leaked secret, a weakened test, rewritten history or a 15,000-line file, enforce it. If it is a matter of style, guide it. Each time the agent breaks a rule, move that rule one step to the right.

SOURCES · COOKBOOK.md:1232-1263, principle 12 at 1664-1665 · code.claude.com/docs/en/best-practices (verified 2026-09-28)

Permissions: deny, ask, allow

Permission rules decide which tool calls run without asking, which ask me first, and which never run. The committed settings file allows checks such as tests, linters, the build and the guard. It asks for commits and package installs. It denies the normal tools from reading secrets, pushing, amending commits, rebasing or resetting history.

The evaluation order is fixed. The docs say: “Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn’t change the order.” A deny at any settings level wins.

The reasoning is practical. The agent can verify its own work without asking me every minute. A commit is my checkpoint. Every new package is a supply-chain decision. Pushing is always my job.

Know the limits. Read and Edit deny rules do not cover a Python or Node script that opens files itself. Rules match command text, not intent, so a differently written push can miss the pattern. Native Windows has no OS-level sandbox. I still keep secrets out of reach: .env is never committed, and .env.example documents only variable names.

WATCH · In bypassPermissions mode explicit ask rules still prompt, but everything else runs without asking, so our guard turns its own “ask” into “deny” there. On Windows every rule is written twice, as Bash(...) and PowerShell(...). Copilot CLI: --deny-tool beats --allow-tool, even with --allow-all.

SOURCES · COOKBOOK.md:155-205 (1.2), 1264-1330 (5.2) · code.claude.com/docs/en/permissions · code.claude.com/docs/en/sandboxing (verified 2026-09-28)

The guard fails closed

If the guard crashes, it blocks.

A hook is a command Claude Code runs at a fixed point: before a tool call, after one, when the agent wants to stop, or when a subagent finishes. Exit code 0 means carry on. Exit code 2 blocks the action, and the error text goes back to Claude as the reason.

Our one hook script is the guard: 370 lines of plain Python. It enforces who writes what, because each of the six roles has its own paths. It protects the files that belong to me: CLAUDE.md, .claude/, .mcp.json and the frozen design contract. It caps file size. It also locks tests after RED, so the developer and debugger cannot make a failing test pass by editing the test. If a test is wrong, they stop and raise a TEST-DISPUTE for me to decide.

The size-limit code uses tighter limits for a few special files and a default entry of 500 lines for a warning and 1,000 for a block. Shrinking an oversized file is always allowed. The old router on the chart had exactly 15,534 lines, so even this deliberately generous limit would have stopped the problem much earlier.

“Fails closed” matters. A hook that crashes with exit code 1 lets the action through, so a broken guard would silently stop guarding. Ours catches any internal error, prints the traceback and exits 2. Test guardrails like code: this guard has its own unit tests, each building a throwaway git repository.

WATCH · A PreToolUse hook only sees the edit tools; an agent can still change a file with sed or rm through the shell. A Stop check therefore scans the working tree with git once per turn. A subagent that tries to finish with an oversized file or a changed locked test is sent back once; the main agent is never blocked, I get a message instead. There are 33 hook events in Claude Code. The research suggested 300/500 as limits; I chose 500/1000.

More engineering, not less

Green proves code matches tests. You confirm intent.

Agentic coding does not replace normal engineering practice. It needs more of it, because nobody reads every line. Every check in this pipeline runs from a command in CLAUDE.md and must pass before a task is done. Most are on the allow list, so the agent runs them without asking.

Tests cover backend behaviour and frontend formatting or components. Ruff catches bugs, import order and style drift. The layer check turns “the domain imports no framework” into an import-linter contract that fails the build. Frontend lint catches rules such as calling the backend outside the API client. The design check catches typical generated UI such as gradients, raw colours and marketing copy. End-to-end runs the real app in a real browser. The guard catches oversized files, changed locked tests and project-structure drift.

At the final gate I still run the app end to end myself. A green suite proves the code matches the tests. Only I can confirm that the tests match my intent.

Let me pick one we have not covered: talk to your agent. Speaking is faster than typing, and it gives the agent more context: the why, the constraints and the doubts, all the things you would never bother to type. Agents are good at turning a rambling voice note into a structured plan. Ask it to repeat back what it understood before it starts. This cookbook started the same way: I dictated the first outline and the agent structured it.

Fail loudly means no silent fallbacks, default values or fake data that hide a failure. Small tasks, fresh context means one task at a time, clear the context between tasks, and if you have corrected the agent twice on the same thing, start again with a better prompt.

Build while you learn

“The hottest new programming language is English”

Open the code
Challenge the agent
Ask why

A question I like to ask is whether we still need to learn Python, TypeScript or any other programming language. My answer is that it is already too late to learn one the old way, language first and projects later. As Andrej Karpathy put it in 2023, “The hottest new programming language is English.”

That does not mean we can skip the skill. We still need the principles of good software engineering and some basic knowledge. What has changed is the order. Ask the agent to create something, collaborate with it, and learn why it chose one approach over another. That only works if you stay curious.

Open the code and read the parts that matter, even if you could not have written them. Challenge the agent: why this library, what breaks when the input is empty, and what would a senior engineer criticise? Ask about every decision, including the ADRs and review findings, until you understand it.

ISSUE-003 is a good example. Asking why a fully green suite missed the VAT bug teaches you what a Python generator is faster than a tutorial chapter. Do this every day and you learn software engineering, and the language along with it.

StarterStandardFull

The cookbook comes with an Agentic Workflow Kit. It is one Agent Skill, so the same folder works in Claude Code, GitHub Copilot, OpenAI Codex and Cursor. Glossary

Agent

An LLM that reads files, runs commands and edits code in a loop until a task is done.

Main agent

The session you talk to. It orchestrates the subagents.

Subagent

A specialised agent with its own context window, started for one job; returns a summary.

CLAUDE.md / AGENTS.md

The instruction file the agent loads at the start of every session.

Skill

A folder with a SKILL.md that describes a repeatable workflow; loaded only when needed.

Hook

A script the harness runs on an event, such as before an edit; it can block the action.

MCP

Model Context Protocol: a standard way to plug tools and data into an agent.

PRP · ADR

Product requirement prompt or plan · architecture decision record, one short file per decision.

RED / GREEN

RED: new tests fail because the feature does not exist. GREEN: the code makes them pass.

Gate

A point where you approve before the workflow continues: spec, tests or final check.

Context window

Everything the model can see at once. It fills up; old content gets compacted or cleared.

Worktree

A second checkout of the same repository, so tasks can run in parallel without collisions.

I keep these definitions here so the workflow terms are easy to look up later.
